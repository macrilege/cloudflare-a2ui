FORD AI CHAT · ADVANTAGES & SPIKE
Should Ford AI Chat use A2UI?
A2UI is a protocol, not a requirement to use Google’s cloud or model. Keep your AI backend and choose a renderer that fits your application.
LayerOfficial integration pathThis demo
RenderingReact, Angular, or Lit renderer + @a2ui/web_coreSmall custom renderer; a deliberate v0.9 subset
Design systemRegister an approved component catalog and themeNative choices, cards, text, and buttons
Agent / AIYour backend; Google ADK is one optional choiceReal AI extracts preferences; application builds the layout
ActionsRoute UI events to authorized application servicesLocal, simulated review and confirmation
The advantages to evaluate
Useful answers: vehicle comparisons, option selectors, and next-step actions can live in the conversation.
Consistent UI: a catalog can map agent requests to approved Ford components. A2UI does not automatically provide Ford styling or accessibility.
Less duplicated integration: a common component-and-state contract may reduce bespoke message formats across use cases. It still needs adapters, tests, and maintenance.
Backend flexibility: the protocol does not require replacing the existing model, agent runtime, or hosting.
Tradeoff: for a small, fixed set of cards, existing component/tool routing may be simpler. A2UI becomes more compelling when multiple journeys or clients need the same contract.
Open the official SDK spike ↗
The spike uses the official Lit renderer and web core, version 0.12.0. Lit fits this framework-free prototype; Ford should evaluate the renderer matching its actual frontend. This is not a recommendation to migrate Ford to Lit.
Research next: try the official renderer in your company’s frontend, map two existing design-system components, and test state, accessibility, invalid output, latency, and action authorization. The dinner tutorial shows the interaction pattern. The separate official-SDK spike tests a bounded Ford vehicle flow; production compatibility and business impact remain unproven.

HONEST ABOUT THE DEMO
Real protocol.
Imaginary restaurants.
Both the guided tutorial and live playground call a real AI service to interpret preferences; the application validates them and constructs A2UI from its approved catalog. This example does not ask the model to invent layouts or write HTML.
Restaurants, seating rules, and availability are fictional. No reservation is made. Live AI shares a 30-request daily allowance; card controls and inspection need no additional AI calls.
For production, connect an authorized availability and booking service, validate actions on the server, and only show success after that service confirms.
